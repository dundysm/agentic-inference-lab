The cliff · KV pool size → prefix reused on resumed turns

Dots are measured (filled = 5-run main cohort, median; hollow = 1-run pilot). The dashed line is the toy LRU model on the right, fed the real request order. Reuse is zero until the pool holds every session's prefix, then it's nearly all of it. Nothing was measured between 43,680 and 58,240 tokens, so the slope there is the model, not data.

Left is evicted first. Sessions run in a circle, so the session that ran longest ago is the one coming up next, and it's sitting at the eviction end. If the pool is short even a little, each new prompt evicts the next session's prefix before that session gets back. Under round robin, LRU throws away the one prefix that's about to be needed.

This is a model, not a trace. Pure LRU on 16-token blocks, one request at a time. vLLM runs 4 in flight and frees blocks tail-first. It still lands on every measured dot, which is why we think this is the mechanism. The measured side backs it up: zero preemptions at every budget, and at 4.5 GiB every resumed turn reused exactly 16 tokens, one shared block.
